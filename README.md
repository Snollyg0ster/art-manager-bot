# mutual-bot

MVP по RFC «Бот учёта взаимных подписок для каналов художников», ревизия 2.

Односторонний сервис: обслуживает одного владельца канала, от контрагента
не требует ничего. Ловит уходы подписчиков, сопоставляет их с журналом мью
и показывает, от каких каналов пора отписаться.

## Статус

Собран и впервые поднят вживую: Colima + `docker compose`, миграция применена,
бот держит long polling.

Проверено на реальном канале, от подписки до записи в журнал:

- `chat_member` доходит (с `allowed_updates`), `join`/`leave` легли в
  `membership_events` с `at_precision='exact'`, проекция `memberships` собралась;
- Redis и расписание сверки (`upsertJobScheduler`) поднимаются;
- **RFC §5.2 закрыт:** `getChat(user_id)` резолвится для пользователя, который
  бота не запускал, и отдаёт `personal_chat` — §8.3 п.1 реализуем и реализован;
- **§8.2 + §8.3 п.1 прошли целиком:** воркер выдержал grace, прислал владельцу
  карточку с автоподставленным каналом, подтверждение кнопкой завело
  `pairs` (broken), `outbound_subs` (mutual) и связь `confidence='manual'`.

Отчёт, раздел новых подписчиков и экран «я отписался» собраны на живой базе
(запросы и рендер проверены, в том числе на подставленном подписчике и на
отписке с откатом данных). Проверено и то, что закрытая пара больше не
воскресает в `broken`: та же задача триажа, что раньше это делала, теперь
завершается молча. Кнопки в Telegram руками ещё не прожаты.

Не проверялось: `reconcileWorker` (§10), импорт на реальном экспорте,
`/delete_me`, ветка `at_precision='window'`, кнопки разбора новых подписчиков.

**Осталось по §10.** Ежесуточная сверка берёт пары в состоянии `watching`.
Такие пары появляются двумя путями: владелец подтвердил нового подписчика или
сработала подстановка контрагента (§8.4). Пары из `/import` + `/label` и `/add`,
по которым контрагент ни разу не появлялся в канале, остаются `unresolved` и
сверкой не покрыты — у них нет `counterpart_user_id`, звать `getChatMember`
не с чем. Это предел метода, а не недоделка: пока человек не сделал ничего
в канале владельца, его `user_id` взять негде (см. §8.5 про пересылку).

**Починено по итогам первого запуска, §14.** Онбординг звал
`getChatAdministrators` прямо в обработчике `my_chat_member` и получал
`400 Bad Request: member list is inaccessible`: в этот момент права бота ещё не
видны Telegram. Повтора не было, ошибка только логировалась, и
`channels.owner_user_id` оставался NULL навсегда — второго `my_chat_member` не
будет, пока права не поменяют руками. С NULL молча умирал весь §8.2:
`triageWorker` выходил на первой строке. Теперь повторы в `fetchChannelOwner` и
ленивый добор владельца в воркере (`ensureChannelOwner`), см.
`src/services/channels.ts`.

## Структура

```
src/index.ts              точка входа бота, long polling
src/config.ts             env + ALLOWED_UPDATES (§5.3)
src/queue.ts              BullMQ: очереди triage/match/reconcile, расписание
src/db/{index,schema}.ts  подключение и схема (§7)
src/bot/index.ts          сборка бота, порядок хэндлеров
src/bot/screens.ts        экраны: текст + кнопки, общие для команд и колбэков
src/bot/handlers/         commands, callbacks, chat-member
src/services/             events, channels, pairs, triage, subscribers, import, report
src/workers/index.ts      triage + reconcile, отдельным процессом
scripts/probe-get-chat.ts блокирующая проверка §5.2
scripts/service.sh        фоновый запуск и остановка, за ним npm run up/down
```

## Запуск

Первый раз:

```bash
cp .env.example .env       # вписать BOT_TOKEN
npm install
docker compose up -d
npm run db:generate && npm run db:migrate
```

Дальше — одна команда на всё:

```bash
npm run up                 # docker + бот + воркеры, фоном
```

Бот и воркеры — два разных процесса, но `npm run up` поднимает оба и ждёт
healthcheck'и Postgres и Redis, чтобы бот не стартовал раньше базы. Запущенное
фоном переживает закрытие консоли: pid-файлы лежат в `.run/`, логи — в `logs/`.

| Команда | Что делает |
|---|---|
| `npm run up` | docker + бот + воркеры фоном |
| `npm run down` | остановить всё, включая контейнеры |
| `npm start` | бот + воркеры фоном (docker уже поднят) |
| `npm stop` | остановить оба процесса |
| `npm run restart` | перезапустить оба |
| `npm run status` | кто жив, с uptime, плюс `docker compose ps` |
| `npm run logs` | `tail -f` по обоим логам |

Любая из них сужается до одного процесса — `bot` или `worker`:

```bash
npm start -- bot
npm stop -- worker
npm run logs -- worker
```

Остановка идёт по `SIGTERM`, у обоих процессов есть обработчик: бот гасит long
polling и закрывает очереди, воркеры дожидаются конца текущей задачи и снимают
lock. `SIGKILL` только если за 10 секунд процесс не ушёл сам.

`npm run down` контейнеры останавливает, но не удаляет — данные и так лежат в
volume, а следующий `npm run up` поднимется быстрее. Снести совсем —
`docker compose down`.

Разработка — по-прежнему в переднем плане, с автоперезапуском на правку файлов:

```bash
npm run dev                # бот
npm run worker             # воркеры, отдельным процессом
```

### Сервер (24/7)

На сервере бот, воркеры и миграции работают в контейнерах из того же
`docker-compose.yml`. Node на хосте не нужен:

```bash
cp .env.example .env       # вписать BOT_TOKEN
docker compose up -d --build
```

Сначала поднимаются `db` и `redis`, затем одноразовый `migrate`
(`drizzle-kit migrate` по закоммиченным миграциям), а после его успешного
завершения стартуют `bot` и `worker`. У всех долгоживущих сервисов стоит
`restart: unless-stopped`: после перезапуска docker они встают сами. Адреса
базы и Redis внутри сети compose задаются в самом compose и перекрывают `.env`.

| Команда | Что делает |
|---|---|
| `docker compose logs -f bot worker` | логи |
| `docker compose restart bot worker` | перезапуск |
| `git pull && docker compose up -d --build` | обновление, миграции применятся сами |
| `docker compose ps -a` | статусы, у `migrate` должно быть `Exited (0)` |

Серверный режим и `npm run up` на одном токене одновременно не запускать: два
long polling дадут `409 Conflict`. `npm run up` поднимает только `db` и
`redis`.

## Порядок работ

Сначала инфраструктура, только потом проба §5.2: `user_id` для неё берётся из
уже пойманного `chat_member`, так что без поднятого бота её не сделать.

1. **(сделано)** Пройти «Запуск» выше и дождаться первого `chat_member`: бота админом в
   тестовый канал, со второго аккаунта (с привязанным личным каналом в профиле
   и **не** нажимая `/start`) подписаться и отписаться. Воркер для этого не
   нужен — событие пишет сам бот, воркер только разбирает уходы.
2. **(сделано, ответ «да»)** **`npm run probe -- <user_id>`** — блокирующая проверка RFC §5.2:
   её результат определяет, будет ли автоподстановка канала в карточке триажа
   (§8.3 п.1). Где взять `user_id` — в шапке `scripts/probe-get-chat.ts`.
   Сам скрипт автономный: нужен только заполненный `.env`, в Postgres и Redis
   он не ходит, запущенный бот ему тоже не требуется.
3. Прогнать реальный экспорт Telegram Desktop через `parseExport` — сверить
   схему `result.json` и формат ID (см. предупреждение в `src/services/import.ts`).

| §7.2 проекция полным реплеем | `projectMembership` |

| §8.3 п.1 подсказка канала из `personal_chat` | `src/services/channels.ts`, карточка в `triage.ts` |
| §8.3 п.3 ручной ввод `@handle` | `src/bot/handlers/callbacks.ts` + `commands.ts` |
| §9 отчёт, разделы + раздел новых подписчиков | `src/services/report.ts` |
| §7 `kind='joined'`: разбор новых подписчиков | `src/services/subscribers.ts` |
| §7 `status='left'`: владелец отписался сам | `dropSub`, `closePair` в `pairs.ts` |
| §8.4 контрагент подставляется при первом событии | `matchWorker`, `resolveCounterpartOnJoin` |

| §13 `/delete_me` стирает лог | `src/bot/handlers/callbacks.ts` |
| §14 онбординг через `getChatAdministrators`, с повторами | `chat-member.ts` + `services/channels.ts` |

§8.3 п.2 (матч по префиксу username) не реализован — отнесён в v1.1 по §14.
Подсказка §8.3 п.1 пишется как `confidence='personal'` и в карточке идёт с
пометкой «предположение»: автоматические действия по RFC разрешены только на
`owner` и `manual`, поэтому канал попадает в журнал лишь после кнопки владельца.

## Осознанные отступления от RFC

- **Long polling вместо вебхука.** `allowed_updates` работает и там, публичный
  URL для MVP не нужен. Переезд на вебхук — один вызов `setWebhook` с тем же
  списком из `ALLOWED_UPDATES`.
- **Парсинг экспорта через `JSON.parse` с лимитом размера.** Стримовый парсер
  (`stream-json`) нужен, когда появятся реальные файлы на сотни мегабайт.
  Пока — лимит и текстовый список как запасной путь.
- **Состояние «жду @handle» лежит в `triage_items.payload`**, а не в отдельной
  FSM. На одну ветку диалога плагин conversations избыточен.
- **Подсказка канала берётся в момент разбора, а не в момент ухода.** Лишний
  `getChat` на карточку, зато свежий `personal_chat` и ни одного вызова на тех,
  кто вернулся внутри grace. Для новых подписчиков — то же самое в момент
  показа, с лимитом 10 вызовов на экран (§5.3) и памятью об отказах до
  перезапуска, иначе каждый отчёт тратил бы вызовы на людей без канала.
- **Всё управление кнопками, команды оставлены дублёрами.** Экран (текст плюс
  клавиатура) описан один раз в `src/bot/screens.ts`, а команда и кнопка меню
  зовут один и тот же экран — расходиться в поведении им нечем. Список команд
  ещё и уезжает в `setMyCommands`, чтобы работало меню «/» в клиенте.
- **Подстановка контрагента (§8.4) живёт в очереди, а не в хэндлере.** На join
  может понадобиться `getChat`, а join — самое частое событие канала; в хэндлере
  это упиралось бы во флуд-контроль §5.3. Плюс дешёвая отсечка: если у владельца
  нет ни одной пары без `counterpart_user_id`, до Telegram дело не доходит.
  Догадку из `personal_chat` бот не применяет молча — спрашивает карточкой,
  потому что §8.3 разрешает автоматику только на `manual` и `owner`, а ошибка
  здесь означает слежку за посторонним человеком.
- **Отписку владельца бот узнаёт только от владельца.** По §12 в аккаунт он не
  лезет, а в Bot API нет метода про подписки пользователя, так что «я отписался»
  — это кнопка. Она ставит `outbound_subs.status='left'` и закрывает пару;
  повторный залив экспорта возвращает запись в `active`, иначе одно нажатие
  запирало бы канал навсегда: `do nothing` его не тронет, а в разметку он
  больше не попадёт.
- **Новые подписчики попадают в очередь `triage_items` с `kind='joined'`.**
  Вид записи зарезервирован в RFC §7, отдельная таблица не нужна: карточка
  живёт ровно затем, чтобы помнить «скрыть» и держать id для кнопок.

## Чего бот не делает и делать не будет

Не подписывается и не отписывается за пользователя — в Bot API этого нет.
Отчёт даёт ссылку, отписывается владелец руками.

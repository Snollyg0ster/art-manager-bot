# RFC: Бот учёта взаимных подписок для каналов художников

| | |
|---|---|
| Статус | Draft, ревизия 2 |
| Дата | 2026-07-25 |
| Автор | Иван |
| Кодовое имя | mutual-bot |

**Изменения в ревизии 2.** Отброшено предположение, что обе стороны мью пользуются ботом. Ручной ввод стал основным путём, сделка через бота — необязательным ускорителем. Импорт экспорта Telegram Desktop поднят из v1.1 в MVP: он единственный даёт полную исходящую сторону. Продуктовая метафора сменилась с «биржа мью» на «журнал с наблюдателем».

---

## 1. Контекст

В сообществе художников распространена практика взаимных подписок («мью»). Договорённость держится на честном слове и рассыпается тихо: вторая сторона отписывается, первая продолжает читать и об этом не знает. Отследить руками невозможно — Telegram не показывает, кто из подписчиков ушёл, и не даёт сопоставить подписчика с его каналом.

Ключевое условие: **контрагент ботом не пользуется и знать о нём не обязан.** Сервис односторонний. Он обслуживает одного владельца канала и не требует ничего от второй стороны.

## 2. Продуктовая метафора

Не биржа и не автоматический арбитр, а **журнал учёта с наблюдателем**:

- **Журнал** — записи владельца о том, с кем он в мью. Заполняется руками, с максимумом подсказок от бота.
- **Наблюдатель** — бот-админ в канале владельца, который ловит уходы подписчиков и приносит их на разбор.

Автоматика здесь не выносит вердикт, а сокращает ручную работу до одного тапа. Всё, что бот не смог определить, он честно кладёт в очередь на разбор, а не додумывает.

## 3. Цели

1. Вести реестр мью владельца с явным уровнем достоверности каждой связи.
2. Ловить уход подписчиков из канала владельца в реальном времени.
3. Сопоставлять ушедшего с записью в журнале и показывать, от какого канала отписаться.
4. Материализовать полный список подписок владельца, чтобы журнал строился поверх реальных данных, а не памяти.
5. Свести ручную разметку к минимуму тапов и никогда не выдавать догадку за факт.

## 4. Не-цели

- Автоматическая подписка и отписка за пользователя — в Bot API невозможна.
- Участие контрагента в системе. Если он тоже пользуется ботом, это бонус (§8.4), не требование.
- MTProto-сессии и доступ к аккаунту владельца.
- Публичные рейтинги и чёрные списки нарушителей (§12).
- Автолайки и автокомментарии — v2, см. §13.

## 5. Ограничения платформы

| Возможность | Доступно боту | Комментарий |
|---|---|---|
| Список участников канала | **Нет** | Метода не существует ни при каких правах |
| Событие входа/выхода | Да | `chat_member`, только с момента добавления бота |
| Проверка участника | Да | `getChatMember(chat_id, user_id)`, нужен известный `user_id` |
| Резолв `@username` → `user_id` | **Нет** | Работает для публичных каналов, не для пользователей |
| Резолв `@channel` → `chat_id` | Да | `getChat('@name')` для публичного канала, членство не нужно |
| Список подписок пользователя | **Нет** | В Bot API отсутствует как понятие |
| Личный канал пользователя | Частично | `getChat(user_id).personal_chat`, см. §5.2 |
| Удалить подписчика | Да | `banChatMember` → `unbanChatMember`, нужен `can_restrict_members` |

### 5.1 Три оси данных и их полнота

Задача распадается на три независимые оси, и полнота у них разная:

| Ось | Источник | Полнота |
|---|---|---|
| На какие каналы подписан владелец | Экспорт Telegram Desktop | **Полная**, на момент экспорта |
| Кто подписан на канал владельца | `chat_member` с момента установки бота | Только дельта |
| Связь «человек ↔ его канал» | Ручная разметка + подсказки | **Частичная, всегда** |

Третья ось — узкое место всей системы, и автоматизировать её до конца нельзя. Отсюда весь дизайн §8: третья ось наполняется в те моменты, когда владелец и так смотрит на человека.

### 5.2 Риск: `personal_chat`

Резолвится ли `getChat(user_id)` для юзера, который засветился только в `chat_member` и не нажимал `/start` — недокументировано.

**Действие до начала разработки:** тестовый бот, тестовый канал, второй аккаунт с привязанным личным каналом, вызов `getChat` по его `user_id`. Полчаса работы. Результат определяет, есть ли в §8.3 автоподстановка канала или там остаётся пустое поле.

### 5.3 Лимиты

- ~30 сообщений в секунду глобально.
- `getChatMember` подпадает под флуд-контроль — сверки батчами с паузами.
- `chat_member` **не приходит без явного** `allowed_updates`. На этом спотыкаются все.

## 7. Модель данных

```sql
users (
  tg_user_id      bigint primary key,
  username        text,
  display_name    text,            -- снимок на момент последнего события
  first_seen_at   timestamptz not null
)

channels (
  chat_id         bigint primary key,
  username        text,
  title           text,
  owner_user_id   bigint references users,   -- nullable
  bot_is_admin    boolean not null default false
)

-- Ось 3. Ядро системы: связь человек ↔ канал с уровнем доверия
user_channel_links (
  user_id     bigint references users,
  chat_id     bigint references channels,
  confidence  text not null,  -- 'owner' | 'manual' | 'personal' | 'guess'
  source      text not null,  -- 'registration' | 'triage' | 'get_chat' | 'forward'
  created_at  timestamptz,
  primary key (user_id, chat_id)
)

-- Ось 1. Подписки владельца. Заполняется экспортом, полная
outbound_subs (
  id             bigserial primary key,
  owner_user_id  bigint references users,
  chat_id        bigint references channels,
  label          text not null,  -- 'mutual' | 'not_mutual' | 'unlabeled'
  status         text not null,  -- 'active' | 'left'
  source         text not null,  -- 'export' | 'manual' | 'deal'
  labeled_at     timestamptz,
  unique (owner_user_id, chat_id)
)

-- Ось 2, источник истины. Append-only, ничего не обновляется и не удаляется
membership_events (
  id            bigserial primary key,
  chat_id       bigint references channels,
  user_id       bigint references users,
  event         text not null,   -- 'join' | 'leave' | 'kick' | 'unban'
  at            timestamptz not null,
  at_precision  text not null,   -- 'exact' | 'window'
  observed_via  text not null,   -- 'chat_member' | 'reconcile' | 'export'
  update_id     bigint unique,   -- дедуп ретраев вебхука; null для reconcile
  created_at    timestamptz not null default now()
)
create index on membership_events (chat_id, user_id, at desc);

-- Проекция текущего состояния. Пересобираема из лога
memberships (
  chat_id        bigint references channels,
  user_id        bigint references users,
  status         text not null,  -- 'member' | 'left' | 'kicked'
  since          timestamptz,
  last_event_id  bigint references membership_events,
  leave_count    int not null default 0,
  primary key (chat_id, user_id)
)

-- Договорённость: соединяет оси 1 и 2 через ось 3
pairs (
  id                   bigserial primary key,
  owner_user_id        bigint references users,
  counterpart_user_id  bigint references users,   -- nullable: канал знаем, человека нет
  counterpart_chat_id  bigint references channels,
  state                text not null,
  note                 text,                      -- заметка владельца
  created_at           timestamptz,
  state_changed_at     timestamptz
)

-- Очередь на ручной разбор
triage_items (
  id          bigserial primary key,
  owner_user_id bigint references users,
  kind        text not null,   -- 'left' | 'joined' | 'unlabeled_sub'
  payload     jsonb not null,
  state       text not null,   -- 'open' | 'resolved' | 'dismissed'
  created_at  timestamptz
)
```

`counterpart_user_id` намеренно nullable. Типичная запись журнала на старте: «я в мью с каналом @artist», а кто им владеет — неизвестно, пока этот человек не совершит действие в канале владельца. Схема обязана переживать такое состояние без костылей.

### 7.1 Состояния пары

| Состояние | Смысл | Действие |
|---|---|---|
| `watching` | Мью записано, обе стороны на месте либо не опровергнуты | — |
| `broken` | Контрагент подтверждённо ушёл | **В список на отписку** |
| `returned` | Ушёл и вернулся, пока владелец не отреагировал | Снять из списка, показать факт |
| `unresolved` | Канал записан, человек не сопоставлен | Ждём события, разбор при появлении |
| `closed` | Владелец отписался, вопрос закрыт | Архив |

`unresolved` — не ошибка и не временное состояние. На старте в нём будет большинство записей, и часть останется там навсегда: если контрагент честно сидит в подписчиках и ничего не делает, событий по нему не будет никогда. Это нормально — молчание означает, что действий не требуется.

`returned` появилось вместе с историей и нужно ровно для одного: не дать владельцу отписаться от того, кто уже вернулся. Без лога такой возврат затирал бы состояние молча.

### 7.2 Семантика лога

**Append-only.** `membership_events` не обновляется никогда. Любое исправление — новое событие. Проекция `memberships` пересобирается из лога полностью, что даёт бесплатную защиту от багов в обработчиках: сломали переход — переиграли проекцию, данные целы.

**Идемпотентность.** Telegram повторяет доставку вебхука при таймауте, и один и тот же выход придёт дважды. Уникального идентификатора у `chat_member` нет, но есть `update_id`, уникальный в рамках бота — его и кладём в unique-индекс. Вставка через `on conflict (update_id) do nothing`, дальше обработка идёт только если строка реально вставилась.

**Восстановленные события.** Ежесуточная сверка (§10) обнаруживает расхождение проекции с реальностью, но не знает, **когда** произошло изменение — только что оно произошло между двумя сверками. Такие события пишутся с `at_precision='window'` и `observed_via='reconcile'`, где `at` — время обнаружения. Смешивать их с точными нельзя: иначе аналитика по времени начнёт врать, а карточка триажа покажет владельцу неверную дату.

**Счётчик уходов.** `leave_count` в проекции — денормализация ради частого запроса «сколько раз этот человек уходил». Считается из лога, хранится для скорости.

**Ретеншен.** Лог не чистится: даже у канала с активной ротацией это десятки тысяч строк в год, партиционирование не нужно. Но `/delete_me` обязан выносить лог наравне со всем остальным (§13).

## 8. Наполнение журнала

Четыре пути, в порядке продуктовой важности.

### 8.1 Импорт экспорта Telegram Desktop — основа

`Settings → Advanced → Export Telegram data`, снять всё кроме списка чатов, загрузить `result.json` боту. Парсер заполняет `outbound_subs(source='export', label='unlabeled')`.

Это даёт ось 1 целиком: владелец видит все свои подписки списком и размечает их пачками — «мью / не мью». Без экспорта журнал строится по памяти, а память у человека с тремя сотнями подписок никакая.

**Проверить перед реализацией:** схема `result.json` и формат ID. В экспорте они могут быть без префикса `-100` — нужна нормализация перед матчингом с `chat_id` из Bot API. Проверяется на одном реальном экспорте.

Разметка не обязана быть разовой: экспорт можно перезаливать, парсер делает upsert, метки сохраняются, новые подписки попадают в `unlabeled`.

### 8.2 Триаж уходов — главный рабочий цикл

Самый ценный момент: подписчик уходит.

```ts
bot.on('chat_member', async (ctx) => {
  const { chat, old_chat_member: o, new_chat_member: n } = ctx.chatMember;
  const type = classify(o.status, n.status);   // 'join' | 'leave' | 'kick' | null
  if (!type) return;

  await upsertUser(n.user);                    // username и имя фиксируем всегда

  // Дедуп ретраев вебхука: обработка идёт только если событие реально новое
  const event = await appendEvent({
    chatId: chat.id, userId: n.user.id, event: type,
    at: new Date(ctx.chatMember.date * 1000), atPrecision: 'exact',
    observedVia: 'chat_member', updateId: ctx.update.update_id,
  });
  if (!event) return;                          // on conflict do nothing

  await projectMembership(chat.id, n.user.id);

  if (type === 'join') return;                 // возврат гасит триаж на этапе воркера
  await queue.add('triage-leave',
    { chatId: chat.id, userId: n.user.id, eventId: event.id },
    { delay: GRACE_MS });                      // 15 мин на случайные выходы
});
```

Воркер `triage-leave` не перепроверяет статус через API, а смотрит в лог: было ли после `eventId` событие `join`. Если было — человек вернулся в пределах grace, пара уходит в `returned` или остаётся `watching`, карточка не создаётся. Лишний вызов `getChatMember` при этом экономится, а решение принимается по данным, а не по гонке между вебхуком и опросом.

Если возврата не было, воркер ищет человека среди пар. Дальше две ветки:

- **Пара найдена** (`counterpart_user_id` совпал) → `broken`, в отчёт с готовой ссылкой на канал.
- **Пары нет** → карточка в `triage_items`:

```
👋 Отписался @artname (Аня Иванова)
   Был подписан с 12.03 (или: до установки бота)
   Уходит не впервые: 3-й раз с марта      ← только если leave_count > 1

   Это мью?
   [Да, канал: @autofill ▾]  [Нет]  [Не помню]
```

Строка про повторные уходы показывается только когда `leave_count > 1`. Соблазн вывести полную историю с датами велик, но это ровно тот случай, когда данные подталкивают к мелочности: владелец начнёт считать чужие уходы вместо того, чтобы решать свой вопрос. Одна строка, без раскрытия — достаточно, чтобы отличить систематическое поведение от случайного тапа.

Здесь и происходит наполнение оси 3 — но не как отдельная скучная работа, а в момент, когда владелец и так смотрит на конкретного человека и решает его судьбу. Ответ «да» создаёт `user_channel_links(confidence='manual')` и сразу переводит пару в `broken`.

Важное следствие: **чтобы поймать нарушителя, не нужно знать о нём заранее.** Подписчик, зашедший до установки бота и никак не размеченный, всё равно даст событие при уходе. Уход — это и есть тот момент, когда информация нужна, и она в этот момент приходит.

Ограничение: если у человека нет `@username` и он сменил отображаемое имя, владелец может его не узнать. Снимок `display_name` и дата подписки в карточке — всё, чем можно помочь.

### 8.3 Подсказка канала

Автоподстановка в поле «канал» карточки триажа, по убыванию качества:

1. `getChat(user_id).personal_chat` — если §5.2 подтвердится.
2. Совпадение `@username` человека с `@username` какого-либо канала из `outbound_subs`. У художников это частый паттерн: `@anna_art` и канал `@anna_art_channel`. Нечёткое совпадение по префиксу, помечается `confidence='guess'`.
3. Ручной ввод `@handle` с валидацией через `getChat` — публичный канал резолвится без членства.

Уровни `personal` и `guess` в отчёте всегда идут с пометкой «предположение» и требуют подтверждения. Автоматическое действие допустимо только на `confidence in ('owner','manual')`.

### 8.4 Сделка через бота — опциональный ускоритель

Если контрагент тоже пользуется ботом, пару можно завести точно и сразу: `/mutual @channel`, бот фиксирует обе стороны, ось 3 заполняется без эвристик. Это приятный частный случай, но **система не должна на него закладываться** — в v1 достаточно вырожденной формы: владелец вручную добавляет пару командой `/add @channel`, а контрагент подставится при первом событии.

### 8.5 Бутстрап `user_id` вручную

Если владельцу нужно проверить конкретного человека, который подписался до установки бота и никуда не уходил, `user_id` можно достать одним способом: владелец пересылает боту любое сообщение от него, бот читает `forward_from`. Дальше `getChatMember` даёт актуальный статус.

Работает не всегда: при включённой приватности пересылок вместо `forward_from` приходит только `forward_sender_name`. Фича нишевая, в MVP не входит, но стоит помнить как единственный обходной путь.

## 9. Отчёт

`/report` и еженедельный дайджест. Порядок разделов фиксирован — сначала то, что требует действия:

```
❌ Отписались от тебя (3)
   @artist_one — ушёл 3 дня назад, ты подписан
   [Открыть канал]  [Отписался, готово]

📥 Требуют разбора (7)
   @artist_two ушёл вчера — это было мью?
   [Да ▾]  [Нет]  [Не помню]

🔍 Не размечено (310 из 340 подписок)
   [Разметить пачкой]

✅ Взаимно (24)
```

Отписывается владелец руками — автоотписки нет и быть не может. Кнопка «Отписался, готово» закрывает пару в `closed`.

Раздел «не размечено» показывает честную цифру. Соблазн её прятать велик — 310 из 340 выглядит как неработающий продукт. Но она и есть правда о системе, а её сокращение с каждой сессией разметки — единственный внятный показатель прогресса для пользователя.

## 10. Периодическая сверка

Ежесуточный джоб проходит по парам в состоянии `watching` с известным `counterpart_user_id` и вызывает `getChatMember`. Ловит случаи, когда вебхук потерялся или бота временно снимали с админства. Батч с паузами, приоритет — пары, по которым давно не было событий.

При расхождении с проекцией пишется событие с `at_precision='window'` и `observed_via='reconcile'` (§7.2), затем проекция пересобирается. Такое событие означает «изменение произошло где-то между прошлой сверкой и сейчас» — карточка триажа обязана показывать это как «ушёл после 24.07», а не выдавать время обнаружения за время ухода.

Пары в `unresolved` сверять нечем: `user_id` неизвестен, а по `@channel` подписчика не проверить.

## 11. Стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Bot framework | grammY + TypeScript | Лучшая типизация апдейтов, `ChatMemberUpdated` корректен |
| БД | PostgreSQL | Реляционная модель с состояниями, транзакции на переходах |
| ORM | Drizzle | Типы выводятся из схемы |
| Очереди | BullMQ + Redis | Grace-периоды, батчи сверки, парсинг экспорта |
| Транспорт | Webhook | Нужен `allowed_updates` и предсказуемый порядок |
| Деплой | Docker Compose на VPS | Масштаб не требует большего |

Парсинг экспорта — потенциально тяжёлый JSON (десятки мегабайт при полном экспорте). Стримовый парсер, отдельный воркер, лимит на размер файла.

## 12. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Владелец не осилит разметку | **Высокая** | Разметка вплетена в триаж (§8.2), а не вынесена в отдельную рутину |
| Владелец не узнаёт ушедшего | Средняя | Снимок имени и даты в карточке; вариант «не помню» без штрафа |
| `getChat` не резолвит незнакомых | Средняя | §8.3 п.2 и п.3 как фолбэк |
| Экспорт слишком муторный для юзера | Средняя | Пошаговая инструкция со скриншотами; система работает и без него, хуже |
| Флуд-контроль на сверках | Средняя | Батчи, бэкофф |
| Ложное обвинение | **Высокая цена** | Grace + перепроверка + разделение разделов отчёта |

Последняя строка главная. Сервис, однажды посоветовавший отписаться от лояльного мью, теряет пользователя навсегда. `unresolved` дешевле ложного `broken`.

## 13. Приватность

- Хранятся `user_id`, `username`, снимок имени и события членства. Никакого контента.
- Данные владельцев не пересекаются: контрагент не видит чужих журналов и не узнаёт, что о нём есть запись.
- `/delete_me` — полное удаление владельца, его связей **и лога событий по его каналу**. Append-only относится к нормальной работе, а не к удалению по запросу: физическое стирание строк здесь обязательно.

Отдельно, и это не формальность: сервис по природе своей ведёт учёт поведения третьих лиц, которые о нём не знают и согласия не давали. Устранить это нельзя — но объём стоит держать минимальным (только факт членства в одном конкретном канале, только по заявленным парам), и не строить поверх этих данных публичных рейтингов или общего чёрного списка.

Решение хранить историю эту границу заметно сдвигает. Одно дело — «сейчас не подписан», другое — поведенческий журнал за год с датами каждого ухода и возврата. Такой датасет уже сам по себе просится в чёрный список, поэтому: наружу из него не отдаётся ничего, кроме счётчика уходов в карточке (§8.2), поисковых и агрегатных запросов «по всем каналам» нет вовсе, а межвладельческие срезы вида «этот человек ушёл у пятерых» не реализуются даже как внутренний инструмент. Ровно та же база, открытая наружу, превращается из инструмента учёта в инструмент травли, а художественные сообщества к этому располагают.

## 14. Этапы

**MVP**
- §5.2 — проверка `getChat` на живом боте, первым делом
- Онбординг: бот админом в канал владельца, `getChatAdministrators` → проверка `creator`
- Импорт экспорта + разметка пачками (§8.1)
- Триаж уходов с grace-периодом (§8.2)
- Отчёт с четырьмя разделами (§9)
- `/add @channel` — ручное добавление пары

**v1.1**
- Подсказки канала: `personal_chat`, матч по префиксу username (§8.3)
- Триаж входов: «новый подписчик @x — это мью?»
- Еженедельный дайджест
- Кик нарушителя по кнопке (`ban` + `unban`)
- Несколько каналов у одного владельца

**v2 — активность**
- Реакции на посты контрагентов через `setMessageReaction` — только для каналов, где бот админ, то есть только для контрагентов внутри системы. При односторонней модели покрытие будет низким, и это ещё один аргумент делать v2 позже и осторожно.
- Комментарии: ловля `is_automatic_forward` в linked-группе, ответ реплаем. Полный автомат делать не стоит — шаблонные «Круто!» под работами считываются мгновенно и работают против репутации канала, ради которой всё затевается. Разумная форма: пуш владельцу с кнопкой быстрой реакции и полем ответа.

## 15. Принятые ограничения

**Слепая зона по «тихим» подписчикам — принята как постоянная.** Подписчики, зашедшие до установки бота и не совершающие действий, системе невидимы. В односторонней модели обойти это нельзя, и обходить не требуется: пока человек не уходит, действий по нему не нужно. Обходные пути (§8.5) остаются точечным инструментом, а не механизмом покрытия.

Следствия для реализации:

- Не строить фичи, требующие полного списка подписчиков.
- В UI не показывать «покрытие подписчиков» как метрику — она неизмерима и будет пугать пользователя без пользы. Метрика прогресса одна: доля размеченных подписок из §9.
- В онбординге сказать прямо: «бот видит уходы начиная с сегодня». Ожидание, выставленное честно на старте, дешевле разочарования на второй неделе.
